# Правила импорта каталога

Источник: `source/Catalog_v11_for_Claude.md` — выгрузка `список v11.xlsx` с адресами ячеек.
Импорт: `npm run import:catalog` → `scripts/import-catalog.mjs`.
Контракт данных: `src/types/catalog.ts`.

Выход (генерируется, руками не править):

| Файл | Что внутри |
|---|---|
| `src/data/products.generated.json` | `Product[]` — витринные товары |
| `src/data/categories.generated.json` | `Category[]` |
| `src/data/source-records.generated.json` | `SourceRecord[]` — **все** непустые строки обоих листов, включая заголовки и примечания |
| `src/data/import-issues.generated.json` | `ImportIssue[]` |
| `src/data/import-report.generated.json` | `ImportReport` — счётчики |
| `src/data/recommendations.generated.json` | `ProductRecommendation[]` — связи из названий + ручные |
| `docs/IMPORT-REPORT.md` | Человекочитаемый отчёт |

Ручной слой: `src/data/overrides.json` — правки, которые импорт накладывает поверх разбора
(скрыть товар, поправить название, добавить рекомендацию, задать фото). Импорт его никогда не
перезаписывает. Повторный импорт того же источника даёт побайтно тот же результат
(детерминированный порядок, без дат и случайных чисел; `sourceHash` — sha256 исходника).

## 1. Чтение

- Таблицы markdown читаются по разделам `## Лист \`1\`` / `## Лист \`2\`` и подразделам `###`.
- Блок определяется по букве ячейки названия: B→`B/C`, E→`E/F`, H→`H/I`, C на листе 2→`C/D`.
- Каждая строка таблицы → `SourceRecord` с `rawText` и `rawPrice` **буквально** (включая
  двойные пробелы, хвостовые пробелы, «М» кириллицей, «!», запятые).
- Классификация строки:
  - `group-header` — B3 «Антенны:» (лист 1) и C3 (лист 2): в ячейке цены стоит заголовок
    колонки «Цена» — он сохраняется в `rawPrice` буквально;
  - `group-header` — также любой текст, оканчивающийся на «:», с пустой ценой (E3, H3, B24,
    B34, B37, B48, C12, C19, C22) и одно слово без цены — «Аттенюатор» (E59, без двоеточия);
  - `note` — прочий текст с пустой ценой: B46 «на МШУ стоят оба sma-female», E57 «на фильтрах
    стоят разъёмы sma male - sma female»;
  - иначе (цена заполнена) `product`.
- Ячейка markdown читается без одного пробела-отступа с каждой стороны: хвостовой пробел текста
  (B13, B15–B17) сохраняется. Адреса ячеек сверяются с номером строки Excel; цена — в соседней
  колонке справа от названия. Нарушение — ошибка импорта.
- `groupHeader` — текст ближайшего заголовка выше в том же блоке (у самих заголовков — null).
  Строка вне группы — ошибка импорта. Для каждой группы есть своё правило разбора по тексту
  заголовка; неизвестная группа или нераспознанный фрагмент строки — ошибка, а не пропуск.
- Контроль: 113 товарных строк на листе 1 (B/C 44, E/F 54, H/I 15) и 19 на листе 2, всего 132.
  Если счёт не сходится — импорт падает с ошибкой.

## 2. Что становится товаром

| Источник | Строк | Товаров | Решение |
|---|---:|---:|---|
| Лист 1 B/C | 44 | 44 | каждая строка — товар |
| Лист 1 E/F | 54 | 50 | E49–E52 — точные повторы E44, E46, E47, E48 (см. примечание ниже) → `merged-duplicate`, второе происхождение у того же товара, проблема `duplicate-row` (по одной на пару) |
| Лист 1 H/I | 15 | 15 | каждая строка — товар |
| Лист 2: Тип1–Тип3, чехлы Тип2–Тип3, M1–M5 | 10 | 0 | `conflict-attached` к товару листа 1 той же модели, проблема `sheet-conflict` с перечнем расхождений |
| Лист 2: чехол Тип1 | 1 | 1 | на листе 1 нет — уникальная позиция, товар с источником лист 2 |
| Лист 2: МШУ 50–6000 МГц | 1 | 1 | на листе 1 такого диапазона нет — уникальная позиция |
| Лист 2: фильтры на объёмных резонаторах | 7 | 7 | отдельная группа, на листе 1 её нет |
| **Итого** | **132** | **118** | |

> **Исправление (сверка с данными).** ТЗ §4 п.5 и прежняя редакция этого документа называли
> оригиналы повторов «E44–E47». По выгрузке E49 = E44 (6100–6500), E50 = E46 (6500–6900),
> E51 = E47 (6400–7100), E52 = E48 (6900–7300); E45 (6300–6500) повтора не имеет. Диапазоны в ТЗ
> перечислены верно — неточен только диапазон ячеек. Импорт сопоставляет строки по буквальному
> тексту и цене внутри блока, поэтому от адресов не зависит.

**Временная витрина = лист 1 + уникальные позиции листа 2.** Это решение для макета (ТЗ §4 п.4),
назначение листов не подтверждено заказчиком. Конфликтующие строки листа 2 не теряются:
они в `source-records`, в проблемах импорта и на служебной странице `/import-report`.

Сопоставление строки листа 2 с товаром листа 1 — по ключу «вид позиции + модель»: антенна —
`Тип1`, мини-антенна — `M1`, чехол — совместимая модель; у позиций без модели (МШУ, фильтры,
кабели) ключ — slug, то есть полный набор характеристик из строки. Одно совпадение →
`conflict-attached`; ни одного → уникальная позиция, товар с источником лист 2; больше одного —
ошибка импорта (неоднозначно). Повтор строки внутри блока — буквальное совпадение текста и цены.

Совпадение диапазона **не объединяет** товары разных групп/цен: фильтры на объёмных резонаторах
1060–1360, 1360–1700, 2100–2700, 3300–3700, 4900–5200, 5200–5500 МГц и полосовые фильтры листа 1
с теми же диапазонами — разные товары (проблема `same-range-different-items`, severity `info`,
одна на диапазон; проверяется среди РЧ-фильтров — у антенн с одинаковым диапазоном товары различает
модель).
Полосовой 2100–2700 встречается дважды и на листе 1: E9 (24 000, N-f/N-f, «на управу») и E20
(17 800) — два разных товара.

## 3. Разбор характеристик

Единицы хранения: частота — МГц; масса — граммы; длина кабеля — см; размер/высота — м; нагрузка — кг.

### Частота `frequency`
- `700-1100 МГц` → range 700–1100 MHz, `confirmed`.
- Диапазон без единицы (`3100-4500`, `136-174`, канальные `3205-3235`) → range в MHz, статус
  `inferred`, note «Единица в прайсе не указана — принята МГц по контексту», проблема `inferred-unit`
  (одна на группу строк, со списком ячеек).
- `6000-8000 ГГц` (B43–B45) → range 6000–8000 с unit `GHz`, статус `needs-review`,
  note «В прайсе указано ГГц — единица уточняется», проблема `disputed-unit` (одна на группу).
  Не пересчитывать. Правило: ГГц со значением ≥ 1000 неправдоподобно для ассортимента и уходит
  на проверку; правдоподобное ГГц (в v11 таких нет) пересчитывается в МГц со статусом `confirmed`.
- Дефис/тире/пробелы вокруг тире не важны.

### Усиление
- Антенны листа 1: `КУ=12 дБи` → `gain_dbi` number 12 dBi; `КУ=7-9 дБи` → range 7–9 dBi;
  `КУ=18,5 дБи` → number 18.5.
- МШУ: `КУ=20 дБ` → `gain_db` number 20 dB. Это усиление, не КУ антенны.
- Лист 2 антенн `КУ=10 дБ` — `gain_db` (дБ не заменяется на дБи); эти строки — конфликтные
  источники, в них разбор хранится для отчёта о расхождениях.

### Разъёмы
Нормализация с сохранением оригинала в `raw`: `N-мама`/`N-f` → `N-female`; `N-m` → `N-male`;
`sma-мама`/`sma-f`/`sma-F`/`sma-female` → `SMA-female`; `sma-m`/`sma male` → `SMA-male`.
- Антенны: `connector` (один разъём).
- Тип8 `N/sma-мама` → `connector` text «N/sma-мама», статус `needs-review`, проблема
  `ambiguous-connector`. Не создавать два разъёма и два SKU. Не участвует в фильтре разъёмов.
- Кабели: `port1_connector`, `port1_shape` («прямой»/«угловой»), `port2_connector`, `port2_shape`.
  Форма не указана (`N-m - N-m`) → характеристики формы нет.
- Полосовые E4–E9 `N-f - N-f` → `port1_connector`/`port2_connector` = N-female, `confirmed`.
- Групповое примечание о разъёмах применяется не дальше своей группы (тот же блок, тот же
  заголовок) и только если не противоречит разъёмам, явно указанным в строках этой группы.
  Товары той же корневой категории вне группы (другие блоки, другой лист) могут подразумеваться
  примечанием — это не утверждается ни в ту, ни в другую сторону, а выносится проблемой
  `group-note-scope` «уточнить».
- B46 «на МШУ стоят оба sma-female» применён к группе «МШУ:» листа 1 (B38–B45) →
  `port1_connector`/`port2_connector` = SMA-female, origin `group-note` `1!B46`, статус
  `confirmed`, `SourceRecord.resolution = group-note-applied`. МШУ листа 2 (C20) стоит в другой
  группе: разъёмы ему не назначены, и это **не** утверждение, что B46 к нему не относится, —
  info-проблема `group-note-scope` «область B46 на лист 2 не распространена — уточнить».
- E57 «на фильтрах стоят разъёмы sma male - sma female» — область действия неясна по ТЗ (§4
  п.12): в своей группе противоречит явным N-f/N-f в E4–E9, а «на фильтрах» может подразумевать
  также канальные (H4–H22) и резонаторные фильтры листа 2 (C23–C29). **Ни к одному товару не
  применено**: в характеристики и фильтр разъёмов не попадает. Сохраняется как `ProductNote`
  (kind `group-note`, `scopeConfirmed: false`) у полосовых фильтров E10–E56 без явных разъёмов
  (43 товара: 47 строк минус 4 повтора); `resolution = group-note-pending`; review-проблема
  `group-note-scope` с перечнем потенциальной области.
- `SourceRecord.productId` у примечаний — null: примечание относится к группе, связь видна по
  `origin` характеристик (B46) и `ProductNote.cell` (E57).

### Прочее
- `IP67` → `ip67` flag `confirmed`. Нет в строке — характеристики нет (не false).
- `XT60` → `power_connector` «XT60».
- Масса: `150 г.`/`150 г` → 150 g; `210 г` → 210 g; `16 кг` → 16000 g; мачта `6 кг` → 6000 g.
- Тип4 `2.5 метра` → `size` 2.5 m (в ТЗ — «размер», не длина).
- Мачта `12 метров (6 кг, нагрузка до 12 кг)` → `height` 12 m, `weight` 6000 g, `max_load` 12 kg;
  `material` «карбон» из заголовка группы «Мачты карбоновые:» (origin `group-header`).
- Аттенюатор `регулировка от 0 до 31 дБ, до 5 Вт` → `attenuation_range` 0–31 dB, `max_power` 5 W.
- Резонаторные фильтры: `0.4 затухание` → `insertion_loss` number 0.4, unit null, статус
  `needs-review`, проблема `unknown-unit`; `ослаб. 50 дБ` → `rejection` 50 dB `confirmed`.
  Код `insertion_loss` — технический идентификатор; в интерфейсе подпись буквально «Затухание»
  (смысл «вносимые потери» не утверждается).
- Кабели: длина `15 см`/`25 см`/`1 м` → `cable_length` 15/25/100 cm; `RG-316 / RG-142` →
  `cable_type` list [RG-316, RG-142], статус `needs-review`, проблема `cable-variants`.
- Конструкция антенны `antenna_design`: логопериодическая (Тип1–4), уголковая (Тип5),
  волновой канал (Тип6), рупорная (Тип7, 8, 10, 12), микро-рупорная (Тип9, 11, 13, 14).
  «Египетская сила» — без конструкции, проблема `unclassified`.
- Модель `model`: «Тип1»…«Тип14», «M1»…«M8». `М8` (кириллица) → model «M8», raw «М8».
- Чехлы: `compatible_model` «Тип1/2/3/7» (из названия, `confirmed`).
- Группа фильтра `filter_group`: «полосовой», «канальный», «на объёмных резонаторах».
- Пометки строк: «(на управу)» (E5–E9), «- под рупор !» (B57) → `ProductNote` kind `row-note`,
  проблема `unclear-note`. В название не попадают.

## 5. Названия, slug, код

- Название строится из исходной строки без выдуманных слов; единица частоты в названии — только
  если она есть в строке. Примеры:
  - «Антенна логопериодическая Тип1», «Антенна «волновой канал» Тип6», «Антенна «египетская
    сила»», «Мини-антенна M8»,
  - «Чехол для антенны Тип2», «Мачта карбоновая 12 м»,
  - «МШУ 700–6100 МГц, 20 дБ, IP67, XT60», «МШУ 6000–8000 ГГц, 10 дБ»,
  - «Кабельная сборка 15 см, SMA-male прямой — SMA-male угловой, RG-316»,
  - «Фильтр полосовой 2200–2500 МГц», «Фильтр полосовой 170–340 МГц, N-female — N-female»,
    «Фильтр полосовой 136–174, N-female — N-female», «Фильтр канальный 3205–3235»,
  - «Фильтр на объёмных резонаторах 1060–1360 МГц»,
  - «Аттенюатор 0–31 дБ, до 5 Вт».
- slug — латиница, детерминированный, уникальный (совпадение slug — ошибка импорта):
  `antenna-tip1`, `antenna-egipetskaya-sila`, `mini-antenna-m8`,
  `cover-tip2`, `mast-carbon-12m`, `lna-700-6100-20db-ip67-xt60`,
  `bandpass-filter-2100-2700-n-female`, `bandpass-filter-2100-2700`, `channel-filter-3205-3235`,
  `cavity-filter-1060-1360`, `cable-15cm-sma-m-straight-sma-m-angled-rg316` и т.п.
- `code` — внутренний код по корневой категории и порядку прайса: `ANT-001`, `CVR-001`,
  `MST-001`, `LNA-001`, `FLT-001`, `CBL-001`, `ATT-001`. Подписывается в интерфейсе как «Код в
  каталоге». Коды и `sortIndex` назначаются до наложения overrides — скрытие товара не сдвигает
  коды остальных.
- Порядок (`sortIndex`) — порядок прайса: лист 1 (B/C, затем E/F, затем H/I), потом уникальные
  позиции листа 2. Поэтому чехол Тип1 (лист 2) — `CVR-004`, МШУ 50–6000 — `LNA-009`.

## 6. Поиск

`searchText` — нормализованная строка (см. `src/lib/search-normalize.ts`, функция используется и
импортом, и поиском): нижний регистр; ё→е; кириллические двойники латиницы в моделях (`М8`→`m8`);
«Тип 1»/«Тип1»/«tip1» → `тип1`; `мгц`/`mhz` → `мгц`; «мама»/`f`/`female` → `female`; `m`/«папа»/
`male` → `male`; запятая в числах → точка; все тире → `-`. В `searchText` входят: название
(и исходное название, если менеджер переименовал товар), модель, исходный текст строк-источников
витрины (`created`, `merged-duplicate`), значения характеристик, названия категорий пути.
Не входят: конфликтные строки листа 2 (иначе запрос «10 дБ» находил бы Тип1 с 12 дБи) и
групповые заметки с неподтверждённой областью (E57 — иначе «sma» находило бы фильтры без
подтверждённых разъёмов). Значение со статусом `inferred`/`needs-review` идёт в поиск только
исходным фрагментом: принятая по контексту «МГц» не находится как написанная в прайсе.

## 7. Рекомендации

Из названий прайса (basis `source-name`, двусторонние): чехол Тип1 ↔ антенна Тип1, Тип2 ↔ Тип2,
Тип3 ↔ Тип3, Тип7 ↔ Тип7. Других автоматических связей нет: совместимость по пересечению
частот не объявляется (ТЗ §7).

`ProductRecommendation.status` (ТЗ §7: черновые связи можно создать, публичная совместимость —
после проверки менеджером):
- связи из названий прайса — `status: 'draft'`;
- запись в `overrides.json` → `recommendations[]` (`productId`, `recommendedId`, необязательные
  `position`, `note`, `status`):
  - для пары, у которой есть черновая связь из названия, — **подтверждает** её: `status` из записи
    (по умолчанию `approved`), `note` и `position` — из записи, если указаны; `basis` остаётся
    `source-name` (откуда связь взялась). Подтверждается одно направление: «чехол → антенна» и
    «антенна → чехол» — разные записи;
  - для другой пары — добавляет ручную связь (`basis: 'manager'`, `status` по умолчанию
    `approved`; `draft` можно указать явно).
- Отбрасываются с предупреждением (консоль, `ImportReport.overrides.warnings`, отчёт): связь
  с несуществующим товаром, товара с самим собой, со скрытым товаром или от скрытого товара —
  включая связи из названий (скрыли антенну Тип2 → пропадают обе связи с чехлом Тип2). Вторая
  запись overrides для той же пары — предупреждение.
- Порядок у товара: сначала связи с `position` из overrides (по ней), затем ручные без позиции,
  затем связи из названий — в порядке прайса; итоговые `position` перенумерованы 1..n.
- `ImportReport.overrides.recommendationsApplied` — ручных связей, `recommendationsApproved` —
  подтверждённых черновых.

## 8. Ручной слой overrides.json

- `products.<id>`: `name` (непустая строка), `hidden` (true/false), `images` (массив путей).
  `hidden: true` убирает товар из `products.generated.json`; строки-источники, проблемы и строка
  в отчёте остаются (помечены «скрыт»). Правка для несуществующего id — предупреждение.
- Неизвестный раздел или поле, неверный тип значения, некорректный JSON — ошибка импорта с
  указанием места (опечатка не должна молча игнорироваться). Ключи `$…` — комментарии.
- `ImportReport.overrides` — sha256 файла, скрытые/переименованные/с фото, число принятых ручных
  и подтверждённых черновых рекомендаций, предупреждения.

## 9. Проблемы импорта и отчёт

Отчёт (ТЗ §4 п.2): `ImportReport.counts` — прочитано (`rowsRead`, `productRows`), создано
(`productsCreated`), объединено/приложено (`mergedDuplicates`, `conflictsAttached`), отправлено на
проверку (`productsWithReviewIssues` — созданных товаров хотя бы с одной проблемой `review` или
`conflict`, включая скрытые; `sourceRowsWithIssues` — строк-источников хотя бы с одной проблемой
любой severity). «Создано/изменено/без изменений/удалено» относительно прошлого
`products.generated.json` (по id товаров) импорт печатает **только в консоль**: в JSON и
`docs/IMPORT-REPORT.md` сверка с прошлым запуском не пишется, иначе повторный импорт того же
источника перестал бы давать побайтно те же файлы.

У всех товарных строк есть `SourceRecord.parsed` — типизированный разбор (`priceType`, `price` в
копейках, характеристики с происхождением): у `created` совпадает с характеристиками товара, у
`merged-duplicate` — разбор строки-повтора, у `conflict-attached` — разбор строки листа 2 (КУ в дБ
остаётся `gain_db`).

`id` = `<code>-<id первой строки-источника>` (`sheet-conflict-s1-B4`), порядок — по severity
(`conflict`, `review`, `info`), затем по порядку прайса. Связи проставлены в обе стороны:
`ImportIssue.sourceIds/productIds` ↔ `SourceRecord.issueIds` / `Product.issueIds`.
